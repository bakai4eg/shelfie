# Рабочий процесс

Договорённости по git и ревью. Цель — чтобы `main` всегда был рабочим, а второй участник понимал чужой код без звонка.

## 1. Ветки

```
main                      всегда зелёный, защищён от прямых пушей
feat/T1.1-auth            новая функциональность
fix/T2.3-cover-upload     исправление бага
docs/api-contract          только документация
chore/ci-ruff             инфраструктура, зависимости, конфиги
```

Правила:

- одна задача = одна ветка = один PR;
- ветка живёт не дольше 5–7 дней; если задача большая — бьём на подзадачи и мержим частями;
- имя задачи в ветке совпадает с ID из `tasks/board.md` (`feat/T3.2-list-showcase`).

## 2. Коммиты

Conventional Commits, заголовок до 72 символов, тело — по желанию:

```
feat(auth): регистрация по логину и e-mail
fix(catalog): не дублировать карточки при повторном поиске
docs(api): описать формат ответа списков
test(library): покрыть смену статуса на «Просмотрено»
chore(deps): обновить fastapi до 0.115
```

Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `style`. Сообщения — по-русски, имена файлов и кода — по-английски.

## 3. Pull Request

1. Обновляем `main`, ребейзим ветку: `git rebase main`.
2. Пушим и открываем PR по шаблону (`.github/pull_request_template.md`).
3. В описании: что сделано, как проверить, какие задачи ТЗ закрыты (`Closes T2.1`).
4. Ревьюер — второй участник, **не автор**. Смотрим: права доступа, ошибки, тесты, соответствие `docs/api.md`.
5. Автор правит замечания, ревьюер аппрувит, автор делает **squash merge** и удаляет ветку.
6. После мержа — статус задачи в `tasks/board.md`.

Что не пройдёт ревью:

- прямой push в `main` и мерж без аппрува;
- PR больше ~400 строк изменений без причины;
- новые эндпоинты без теста и без строки в `docs/api.md`;
- миграция, меняющая уже применённую;
- закомментированный код, `print`, секреты, `.env`.

## 4. CI (`.github/workflows/ci.yml`)

Запускается на каждый PR и push в `main`:

| Джоб | Что делает |
| --- | --- |
| `backend` | ставит зависимости, `ruff check`, `pytest` на SQLite |
| `frontend` | `npm ci`, `tsc --noEmit`, `npm run build` |

Красный CI = PR не мержим. Если тест падает «на главной» — сначала чиним `main`, потом занимаемся фичами.

## 5. Миграции

- Одна миграция — один PR (если только правки не связаны).
- Генерируем: `alembic revision --autogenerate -m "add lists"`, затем **читаем** сгенерированное и правим руками.
- Имя: `0004_add_lists.py`, внутри — `upgrade()` и `downgrade()`.
- Перед мержем проверяем на чистой БД: `alembic upgrade head` с нуля.
- Данные не удаляем миграцией без обсуждения — сначала обсуждаем в PR.

## 7. Задачи и метки

GitHub Issues повторяют карточки из `tasks/`: заголовок `T2.1 Каталог, поиск, фильтры`, тело — содержимое файла задачи, метки: `stage-2`, `backend`/`frontend`, `bakai`/`elvina`.

Статусы: `backlog` → `in progress` → `review` → `done`. Доска — GitHub Projects или таблица в `tasks/board.md` (обновляется в том же PR, что закрывает задачу).

## 8. Полезные команды

```bash
# синхронизировать ветку с main
git fetch origin && git rebase origin/main

# посмотреть, что войдёт в PR
git log --oneline origin/main..HEAD

# переименовать ветку под правила
git branch -m feat/T1.1-auth

# запустить всё локально перед PR
cd backend && ruff check . && pytest -q
cd frontend && npm run typecheck && npm run build
```

## 9. Если что-то сломалось

- Коммит уже в `main`, но сломал сборку → `git revert <sha>` отдельным PR, разбор после.
- Секрет попал в коммит → немедленно меняем ключ, потом чистим историю (предупредить второго участника).
- Конфликты в миграциях → пересоздаём миграцию поверх актуального `main`, не «мержим руками» в `versions/`.

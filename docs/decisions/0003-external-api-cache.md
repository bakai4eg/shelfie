# 0003. Кэш внешних источников в собственной БД

- **Дата:** 2026-10-21
- **Статус:** accepted
- **Участники:** Бакай, Эльвина

## Контекст

ТЗ 4.3.2 требует: сохранять данные внешних источников в своей БД, обслуживать повторные обращения из неё, обновлять устаревшие данные при обращении, если источник доступен. ТЗ 2.3 прямо называет зависимость от внешних API риском.

## Варианты

1. **Redis как кэш** — быстрый TTL, но четвёртый сервис в compose и ещё одна точка отказа.
2. **Кэш в `catalog_items.fetched_at`** — данные и так нужны в БД для полок и рецензий.
3. **Кэш в отдельной таблице `external_cache`** — чище по слоям, но дублирует карточки.

## Решение

Вариант 2. Карточка из источника сразу становится обычной записью каталога. `fetched_at` + `CACHE_TTL_DAYS` определяют устаревание; свежесть проверяем при чтении.

## Последствия

- Минус один сервис в инфраструктуре и одна зависимость.
- Обновление устаревших карточек делаем «лениво», при обращении, а не планировщиком.
- Если источник недоступен, отдаём то, что есть, и логируем предупреждение — 200 с частичным результатом.
- Нужны тесты на дедупликацию по `(source, external_id)`.
